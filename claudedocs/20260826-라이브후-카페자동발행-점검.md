## 2. 원인 (전부 운영기에서 직접 확인)

### 2-1. 모니터가 파이프라인이 아니라 하위 러너를 불렀다 — 이게 핵심

카페 단계는 `run-scheduled-pipeline.mjs`에만 있습니다. 그런데 8/20에 추가된 자기치유 모니터
`run-scheduled-monitor.mjs`는 `run-scheduled-live.mjs`(라이브 전용)를 직접 호출했습니다.

정규 슬롯 3개가 매주 실패하니 실제로 일하는 건 모니터뿐인데,
**모니터 경로에는 카페 단계가 아예 없었습니다.** 게다가 라이브 상태만 보고 `exit=0`으로 닫아
아무도 이상을 눈치채지 못했습니다.

### 2-2. 카페 플래그가 `mode: "dry"`에 멈춰 있었다

```
"cafePublisher": { "enabled": true, "mode": "dry", "notify": false, ... }
```

`enabled: true`라 켜진 것처럼 보이지만 `dry`는 원고와 장면만 만들고 **네이버에 아무것도 쓰지 않습니다.**
운영 전환 절차의 3단계에서 멈춰 있었습니다.

### 2-3. 운영기가 자기 브랜치 갱신을 받을 수 없는 상태였다

운영기는 `codex/live-replay-self-heal-20260820` 브랜치인데, partial clone의 fetch refspec이
**옛 브랜치 하나에만 고정**돼 있었습니다.

```
remote.origin.fetch = +refs/heads/codex/live-replay-session-refresh:refs/remotes/origin/...
```

upstream도 없어서 `git pull`은 엉뚱한 기본 브랜치를 당기고 `not possible to fast-forward`로 실패했습니다.
개발기(맥)의 수정이 운영기에 도달할 방법이 없었습니다.

### 2-4. 정규 슬롯이 매주 실패하는 별개 문제

03:10은 라이브 종료 약 6시간 뒤인데, 그 시점에 YouTube Studio 다운로드 링크가 아직 없습니다.
10:10까지도 없었고 11:30에야 가능했습니다. 그래서 사실상 모니터 전용 운영이 되어 있었고,
2-1 때문에 카페가 통째로 유실됐습니다.

> 8/18 라이브 글(#5959)이 카페에 있는 건 8/21 00:37에 **사람이 발행기를 손으로 돌린 것**입니다.
> 발행기 자체는 검증됐다는 뜻이고, 실제로 이번에도 원고·장면 생성까지 정상 동작했습니다.
