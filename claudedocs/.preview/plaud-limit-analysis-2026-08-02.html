거절 시 지금처럼 6시간 라이브는 매번 수동으로 구간 잘라 2번 보내야 함

1. 실측한 사실

항목 값
실패한 job c80d06cc666c1559
실패 메시지 PLAUD Web import는 최대 5시간까지 지원합니다
차단 위치 server/plaud/extension-upload.js:473 (segmentSeconds > plaudMaxSeconds)
영상 길이 22403초 = 6시간 13분 23초
같은 영상 MP3 단일 다운로드 512.8MB (192kbps 스테레오)
같은 영상 2분할 각 256.4MB

즉 PLAUD 업로드는 시작도 못 했다. 서버가 5시간 룰로 먼저 막았다.

2. 용량 문제는 생각보다 작다

PLAUD 전송 경로는 재인코딩을 하지 않고 YouTube 원본 오디오를 그대로 쓴다.

// extension-upload.js:40
'-f', 'bestaudio[ext=m4a]/bestaudio',

512.8MB는 MP3 192kbps로 재인코딩하는 일반 다운로드 경로의 숫자지, PLAUD 경로 숫자가 아니다.

경로 6시간 13분 5시간(제한 상한)
MP3 192kbps 스테레오 (일반 다운로드) 512.8MB (실측) 약 432MB
m4a 원본 약 129kbps (PLAUD 경로) 약 361MB 약 290MB
모노 64kbps AAC 약 172MB 약 144MB
모노 32kbps AAC 약 86MB 약 72MB

결론: 5시간 룰을 지키면 PLAUD 경로 용량은 대개 290MB 선. 500MB에 닿으려면 원본이 256kbps급이어야 하는데 드물다. 500MB 가드는 안전망이지 주 대책이 아니다.

3. "음질 손실 없이"에 대한 정직한 답

  • 재인코딩하면 손실은 반드시 생긴다. 무손실이라고 말하면 거짓말이다.
  • 그런데 PLAUD는 전사(STT)용이다. STT 엔진은 내부적으로 16kHz 모노로 다운샘플해서 처리한다. 음악 감상용 192kbps 스테레오는 전사 관점에서 완전한 낭비다.
  • 즉 "음질 손실 없이"가 아니라 "전사 품질 손실 없이"가 실제로 원하는 것이고, 그건 모노 64kbps로도 달성된다.
  • 게다가 아래 1순위 안은 재인코딩 자체를 안 한다(스트림 복사로 자르기) — 손실 0.

4. 제안 구조

PLAUD 전송 버튼을 누르면 서버가 스스로 판단:

duration 확인
├─ 5시간 이하 & 예상 500MB 이하 → 지금 그대로 (재인코딩 0, 가장 안전)
├─ 5시간 이하 & 500MB 초과      → 모노 64kbps AAC 재인코딩 후 업로드
└─ 5시간 초과                    → 자동 N분할(파트당 4.5시간 이하) → 순차 업로드
                                   → 파트별 transcript 수신 → 시간순 병합
                                   → 병합본 1개를 insight-processor에 투입

분할 경계 처리 (기본값으로 채택)

목표 지점 ±60초 안에서 ffmpeg silencedetect로 가장 긴 무음을 찾아 그 지점에서 자른다. 말 중간이 잘려 전사가 깨지는 걸 막는다. 무음이 없으면 균등 분할로 폴백.

  • 오버랩 방식(30초 겹치기)은 채택하지 않음 — 중복 문장이 인사이트 추출을 오염시킨다.
  • 자르기는 -c copy 스트림 복사 → 재인코딩 없음 → 음질 손실 0.

파트 제목

제목 (1/2), 제목 (2/2) 형태. PLAUD 목록에서 식별 가능해야 병합 시 순서를 잡을 수 있다.

5. 숨은 비용 (여기가 진짜 작업량)

현재 인사이트 파이프라인은 단일 파일 전제다.

// extension-upload.js:458
spawnInsightProcessor(job.downloadPath, fileTitleFromJob(job), job.plaudFileId)

분할하면 job.downloadPath가 파트 수만큼 생긴다. 그대로 두면 6시간 라이브의 인사이트가 앞뒤 따로 반쪽씩 나온다.

필요 작업: 파트 transcript 전부 수신 대기 → 시간 오프셋 보정해서 concat → 단일 transcript 파일 생성 → 그걸 insight-processor에 넘김.

6. 작업량 추정

단계 라운드
5시간 초과 자동 분할 + 순차 업로드 2~3 라운드
transcript 병합 + 인사이트 파이프라인 연결 2~3 라운드
500MB 초과 시 모노 64kbps 재인코딩 가드 1 라운드
실제 6시간 라이브로 종단 검증 1 라운드 + PLAUD 전사 대기(외부 시계, 수십 분)

미해결 시 에스컬레이션: PLAUD Web이 연속 업로드를 rate limit으로 막으면 파트 간 대기 삽입.

7. 우선순위 의견

  1. 5시간 자동 분할 + transcript 병합 — 실제로 막힌 것. 이것만 해도 문제가 사라진다.
  2. 500MB 재인코딩 가드 — 안전망. 거의 발동 안 하지만 발동 시 확실히 살려준다.
  3. 일반 다운로드 경로(MP3 192kbps)는 PLAUD와 무관하니 건드리지 않는다.
